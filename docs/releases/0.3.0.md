# Jev Java 0.3.0

Adds OpenAI's beta Decisions API while preserving existing Jev clients and
Java 17 compatibility.

## OpenAI Decisions

- New `jev-openai` module and `OpenAiJevClient`; default model `gpt-6-luna`,
  `OPENAI_API_KEY`, and `/v1/decisions`.
- Native `decide` / `decideAsync` supports text and inline images, string/boolean
  choices, score descriptions, optional names, request-level safety identifiers,
  ordered partial-refusal results, complete usage, and raw provider metadata.
- Existing `evaluate` / `evaluateAsync` supports basic Noul, string/enum Choice,
  string-level Score, and compatible Java record schemas with text input.
- Spring `jev.provider=openai`, typed client injection and optional lazy
  `ReactorOpenAiClient`. All paths retain cancellation and transport ownership.

See the [configuration and API guide](../openai-decisions.md).

## Compatibility

The new `JevException.Kind.REFUSAL` represents a refused compatibility evaluation.
Consumers with exhaustive switches over `Kind` must handle it. Native requests
instead retain `DecisionAnswer.Refusal` alongside successful sibling answers.
The existing sealed `Question` and `Answer` hierarchies are unchanged.

Generic Jev methods reject structured instructions/criteria, images and
`@JevLabels` on OpenAI before HTTP. Native Decisions types cover the endpoint's
own feature set; they do not convert arbitrary JSON state into prompts.
Core still has no Spring dependency, and existing provider formats are unchanged.

## Validation and availability

304 offline tests cover contracts, malformed payloads, lifecycle behavior and
Spring integration. Tests and examples require no provider credentials unless
explicitly running a live example. See [validation evidence](../validation.md)
for runtime matrix and packaging checks.

Live verification was blocked by this account's `429 billing_not_active` response.
Successful live text/image inference is not claimed. Examples and synthetic
fixtures are not accuracy or latency benchmarks.

The manual Maven Central workflow now offers explicit `publish` for an existing
public release tag whose version matches the POM. Default `verify` and the
manual-Portal `upload` operation retain their previous behavior.
